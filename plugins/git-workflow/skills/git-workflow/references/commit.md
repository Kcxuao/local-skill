# Commit

用户明确要求提交时，创建本地 Commit；仅要求提交信息时，只生成文本。

## 提交信息规范

```text
<type>：<简洁的中文变更描述>

- 1. <实际实现或修改内容>
- 2. <实际实现或修改内容>
```

- 类型：`feat` 新功能、`fix` 问题修复、`init` 项目初始化、`refactor` 重构、`perf` 性能优化、`docs` 文档、`test` 测试、`chore` 常规维护、`build` 构建与依赖。
- 根据**变更目的**选择主要类型，优先遵循仓库现有提交约定。
- 标题突出本次提交的主要成果；标题与正文之间保留**一个空行**。
- 正文按 `- 1. `、`- 2. ` 顺序编号，通常 1～5 项，描述已实现的功能或行为，不按文件逐项罗列、不虚构结果。

示例：

```text
feat：新增用户权限认证功能

- 1. 实现 JWT Token 签发和校验
- 2. 新增认证拦截与角色权限控制
```

## 执行流程

1. **检查**：查看 `git status`、暂存与未暂存 Diff；对未跟踪文件按需读取内容。先用统计信息确定范围，再按需查看具体差异。
2. **划定范围**：仅纳入本次任务相关修改。保护已有暂存内容；若不同任务混在同一文件或暂存区且无法安全分离，先确认。无变更则不创建空提交。
3. **精确暂存**：只暂存确认属于本次提交的文件或代码片段，不使用无差别的 `git add .` / `git add -A`。检查最终 `git diff --cached` 与 `git diff --cached --check`。
4. **生成并提交**：以最终暂存内容生成上述中文信息，执行 `git commit`；不自动 Push、Amend 或跳过 Hooks。提交失败时保留当前状态并报告原因。
5. **核验**：检查最新 Commit 内容及 `git status`，报告 Hash、提交摘要和剩余未提交变更。

默认一个任务对应一个逻辑 Commit；明显无关的变更应隔离，不能安全隔离时不猜测提交范围。只请求生成信息时执行步骤 1～2，并根据相关差异草拟内容，不暂存、不提交。
